PART 1 - WELCOME TO ROBOT OPERATING SYSTEMS

Hello everyone, and welcome to AI 304, Robot Operating Systems. If robotics is the body and artificial intelligence is the mind, then the robot operating system is the nervous system that ties everything together. This course is intensely practical: by the end you will be able to set up, program, and debug real robotic software systems using the Robot Operating System, the global standard platform known as ROS. I am excited to guide you through it, and as always we will connect everything to real life practicals and examples from Nigeria and Africa.

First, a clarification. When we say Robot Operating System, or ROS, it is not an operating system in the sense of Windows or Linux. It is a flexible framework, a set of tools, libraries, and conventions that helps you build robot software. It runs on top of Linux and provides the plumbing for complex robot programs to work together: how different parts of a robot communicate, how they are started and managed, how they share data, and how developers reuse each other's work. Learning ROS is learning the professional craft of robot software engineering.

Why does robotics need such a framework? Because a real robot is a symphony of concurrent processes. One program reads the laser scanner. Another computes the robot's position on a map. Another plans a path to the goal. Another controls the motors. Another builds a map of the room. Another handles camera vision. Each of these is a complex program in itself, and they must all run together, share data with millisecond timing, recover from crashes, and be developed by different team members. Writing all of that plumbing from scratch for every robot is wasteful and error prone. ROS provides the plumbing once, well, so you can focus on your robot's unique intelligence.

Let me share real life practicals to show the value. A team building a delivery robot in Lagos uses ROS to connect lidar mapping, localization, path planning, and motor control modules that were written by different engineers on different continents. A university in Nigeria teaching robotics uses ROS with low cost robots so students run the same code that professionals use in industry. An agriculture robotics startup reuses open source ROS packages for navigation and adds their own crop inspection node. A research group simulates a full robot in a physics simulator through ROS before building hardware, saving months and thousands of dollars. ROS is the common language of modern robotics.

We will study the communication mechanisms in depth and learn to choose between them. We will explore the standard tools for debugging, visualization, and recording. We will program robots: writing nodes in Python and C plus plus, reading sensors, and commanding actuators. We will study the important ecosystems: robot modeling with description files, simulation with Gazebo, navigation stacks, and perception pipelines. We will cover packages, workspaces, and the build system that organize real projects. We will address real time, embedded, and multi robot considerations. And we will close with best practices, careers, and reflections.

A note on versions. ROS one is the classic version with the rich ecosystem you will mostly learn from. ROS two, now the modern standard, adds security, real time support, and multi robot reliability while keeping the core concepts you learn here. This course teaches concepts and practices that transfer directly between them; we will note key differences along the way.

To succeed in this course, adopt the habits of a systems engineer. Break complex systems into communicating parts. Test each part separately before integrating. Read error messages carefully. PART 2 - CORE CONCEPTS AND ARCHITECTURE OF ROS

Let me walk you through the core concepts and architecture of ROS, the foundation everything else builds on.

The basic unit of ROS software is the node. A node is a program that does one thing well: one node reads the laser scanner, one node computes odometry, one node controls the motors. Nodes are small, focused, and replaceable. This design philosophy comes from Unix: make each program do one thing well, and compose programs that work together. In ROS, nodes can be written in different languages and run on different computers, yet all cooperate.

Nodes communicate by passing messages. The communication patterns are the heart of ROS. Let me explain the three main ones.

Topics are for continuous data streams, a publish subscribe model. One node publishes messages on a topic, like camera images on the camera topic. Any number of other nodes subscribe to that topic and receive the messages. Publishers do not know who is listening; subscribers do not know who is publishing. This decoupling is powerful. Examples: laser scans streamed continuously, robot pose streamed continuously, camera images streamed continuously. Topics are asynchronous and one directional, ideal for sensor data and state streams.

Services are for request response interactions, like remote function calls. One node provides a service; another node sends a request and waits for the response. Examples: asking the map server for the current map, commanding a gripper to open and receiving success or failure. Services are synchronous and two way, ideal for actions that need confirmation.

Actions are for long running goals with feedback. When you command a robot to drive to a distant point, the motion takes time and you want progress updates and the ability to cancel. Actions provide exactly this: a goal is sent, feedback streams back, and a final result arrives. Navigation is the classic action in ROS: send a goal pose, watch the robot progress, receive arrival confirmation.

Parameters let you configure nodes without changing code: the robot's wheel diameter, the maximum speed, the map file path. Parameters live on a parameter server and can be set at launch time. Good robotics code reads configuration from parameters rather than hard coded values.

The ROS master is the matchmaker. When a node wants to publish on a topic or offer a service, it registers with the master. When another node wants to subscribe or call, it looks up the connection through the master. The master connects the parties, and then they talk directly. In ROS two, discovery is decentralized, removing the master bottleneck while keeping the concepts.

The file system level organization matters too. ROS software is organized into packages, the unit of sharing: a package might contain a driver node, message definitions, and launch files. Packages are built with a build system called catkin in ROS one and colcon in ROS two. A workspace is your working directory with your packages.

Let me describe the graph view of a running system. Imagine your robot running: the camera node publishes images; the vision node subscribes and publishes detected objects; the planner node subscribes to objects and odometry and publishes velocity commands; the motor node subscribes and drives wheels. This directed graph of nodes and topics is your robot's software architecture, and ROS provides tools to visualize it live.

Real life practicals. A Nigerian robotics team debugging a warehouse robot inspects the node graph and discovers the planner never receives odometry because of a topic name mismatch, the single most common ROS error. A student sets parameters for maximum speed at launch time, so the same code serves slow indoor and faster outdoor robots without editing source. Architecture thinking pays: sketch your node graph on paper before writing code, deciding what nodes exist and what they publish and subscribe to.

One more core concept: time and clocks. All ROS messages carry timestamps, and nodes use a shared notion of time for synchronization. Simulations can run on simulated time, letting you test timing sensitive code faithfully. Master time early; it governs everything.

PART 3 - SETTING UP YOUR ROS ENVIRONMENT

Let me walk you through setting up a working ROS development environment, because practical skill begins with a working system.

ROS runs primarily on Linux, and the recommended distribution is Ubuntu with its matching ROS distribution. The classic pairing is Ubuntu with ROS one distributions like Melodic or Noetic, and Ubuntu with ROS two distributions like Humble or Iron. Use a matching pair; mismatched versions cause mysterious failures. Installation is done through the package manager: add the ROS repository, install the packages, and configure your shell.

Setting up the workspace is the next step. For ROS one, create a catkin workspace folder with a source subfolder, put your packages inside, and run catkin make to build. For ROS two, create a workspace and use colcon build. After building, source the setup file so your shell knows where the packages are. This sourcing step is the number one beginner hurdle: if commands are not found, you almost certainly forgot to source your setup file.

Environment variables carry configuration. The ROS distribution name, the master location, and your package paths are all environment variables. Multi machine setups configure the master location so nodes on different computers find each other. Understanding these variables demystifies ROS.

Installation options for different situations. Native installation on Ubuntu gives the best experience. A virtual machine offers safety and convenience on Windows or Mac hosts, at some performance cost for simulation and vision. Windows Subsystem for Linux two provides a good middle path on modern Windows. Docker containers package reproducible environments, excellent for teams and classrooms. Cloud and remote development lets you run heavy simulation on a server and code from a laptop.

Your first working system deserves a careful test. Install the tutorials package and run the classic talker and listener example: one node publishes messages, another prints them. If the listener prints the talker's messages, your installation, environment, and networking are healthy. Celebrate this moment.

Essential companion tools to install: the build tools, the visualization tool called RViz, the simulation tool Gazebo, and the robot models and tutorials packages. These give you the standard development environment.

Troubleshooting skills matter as much as installation. The most common problems are forgetting to source the setup file, using the wrong distribution name, having stale processes still running, and firewall or network configuration blocking communication between machines. Search the community answers; the ROS community is large and helpful. Keep a personal troubleshooting log; it will save you hours.

Real life practicals. A Nigerian university sets up a robotics lab with identical Docker based ROS environments on every student machine, ending version conflicts and speeding setup from days to minutes. A student installs ROS in a virtual machine on a modest laptop and successfully runs simulation with reduced graphics settings. A remote team in Ibadan and Abuja collaborates over a shared ROS workspace using version control and containers. Build your environment once, document it, and share it with your team.

A practical habit: script your setup. Write a shell script that installs everything and a README with exact steps. Future you, and every teammate, will benefit enormously.

PART 4 - COMMUNICATION IN DEPTH: TOPICS, SERVICES, ACTIONS, PARAMETERS

Let me deepen your mastery of ROS communication, because choosing the right mechanism separates elegant systems from fragile ones.

Topics serve continuous streams. Let me describe them in engineering detail. Messages on topics have defined types: a laser scan message contains ranges and angles; a pose message contains position and orientation; an image message contains pixel data. You can define your own message types for your robot's needs. Topics support queues: if a subscriber processes messages slower than they arrive, messages queue up and old ones may be dropped, keeping fresh data flowing. For sensor streams, dropping old data is correct; for commands, you need reliability.

Publishers and subscribers can be many to many: one laser node publishing, and localization, mapping, and obstacle avoidance all subscribing. This fan out is one of ROS's great strengths: one computation, many consumers.

Let me give practical guidance on topics. Give topics clear names organized by robot part: robot one laser scan, robot one cmd vel. Use standard message types where they exist so your nodes interoperate with the ecosystem. Keep message rates reasonable: one hundred hertz for control, ten hertz for many sensors. And beware of latency: large messages like images strain networks; compress when needed.

Services provide request response for discrete interactions. A service has a request type and a response type: the request might contain a target file name, the response a success flag. Services are synchronous: the caller waits. Use services for operations that need a definite answer and complete quickly: saving a map, resetting a controller, querying a configuration. Avoid services for long operations, because the waiting caller blocks.

Actions extend services to long running, goal directed tasks with feedback and cancellation. An action has a goal, feedback messages during execution, and a result at the end. Navigation to a pose, executing a trajectory, or a long grasp sequence are actions. The action interface includes the ability to preempt, to cancel or replace the goal, essential when plans change.

Parameters configure nodes. Best practice: declare every tunable as a parameter with a sensible default. Group parameters in configuration files loaded at launch. ROS two adds parameter services allowing live reconfiguration and typed parameters for safety.

Launch files orchestrate systems. A launch file describes which nodes to start, with which parameters, remappings, and settings. One launch command can bring up an entire robot: drivers, localization, navigation, visualization. Write launch files for every stage of development: simulation launch, real robot launch, single robot, multi robot.

Namespaces and remapping organize complexity. Namespaces group topics and nodes: robot one and robot two namespaces let the same code run for multiple robots without collision. Remapping redirects topics: your navigation node expects scan data; you remap that expectation to your robot's actual scanner topic. Mastering namespaces and remapping is a milestone in ROS fluency.

Real life practicals. A Lagos robotics team uses topics for continuous lidar and camera streams, a service to reset the navigation planner after a blocked path, an action for the drive to goal behavior, and parameters for maximum speeds, all orchestrated in launch files that switch between simulation and the real robot with one flag. A student debugs a slow vision pipeline by inspecting queue behavior and switching to compressed image topics over the network. Choose mechanisms deliberately: streams on topics, quick exchanges on services, long missions as actions.

PART 5 - TOOLS FOR DEBUGGING, VISUALIZATION, AND RECORDING

Let me walk you through the professional tooling that makes ROS development efficient and even enjoyable.

Visualization begins with the graph tool that shows running nodes and their topic connections. When something does not work, first inspect the graph: is the node running, are the topics connected with the names you expect, is anything publishing. This single habit resolves a large fraction of integration problems.

RViz is the visual window into your robot's world. It displays robot models, laser scans, camera images, maps, planned paths, coordinate frames, and markers you draw for debugging. Configure RViz with panels for exactly what you need, and save your configuration in the package so teammates share your view. RViz is also interactive: you can set navigation goals by clicking, a delightful debugging experience.

Recording and replay is one of ROS's superpowers. The bag tool records topic data to files and plays it back later. Record a problematic run on the real robot, then replay it at your desk while changing your algorithm and testing fixes, without redeploying hardware. Bags are also for sharing datasets and creating regression tests: record once, replay forever, and verify your code handles the recorded reality.

Command line tools give direct access. You can list nodes, topics, and services; echo topic messages to the console; inspect message types; and send service calls and messages manually. Manual message sending is superb for testing: command a motor directly and watch the robot move before your controller is ready. Parameter tools let you read and set parameters live.

Logging is essential. Every node should log informative messages at appropriate severity levels: debug for development detail, info for normal milestones, warn for surprises, error for failures. Read logs first when debugging. Log files from real runs are gold for post mortem analysis.

Profiler and timing tools help optimization. Measure how long your node callbacks take and how much CPU and memory they use. Real robot computers are modest; efficient code keeps loops timely. Profile before optimizing; intuition about bottlenecks is often wrong.

Real life practicals. A Nigerian robotics startup keeps recorded bag files of every field incident, so engineers replay failures on Monday morning and fix them without repeating the field trip. A student uses RViz to discover her localization frames are misaligned, visible instantly as laser scans not matching the map. A team uses command line tools to test a gripper driver independently before integrating grasping software. Invest time in tools; they repay tenfold.

A practical habit: create a standard debugging checklist for your robot: check the node graph, echo key topics, inspect the transform tree, view in RViz, read the logs, and replay bags. Systematic debugging beats random thrashing every time.

PART 6 - PROGRAMMING NODES: PYTHON AND C PLUS PLUS

Let me walk you through the actual craft of programming ROS nodes, the daily work of a robotics software engineer.

ROS supports multiple languages, primarily Python and C plus plus. Python is quick to write, excellent for prototyping, glue logic, and high level behaviors. C plus plus is fast and deterministic, ideal for control loops, drivers, and performance critical processing. Professional robots often mix both: C plus plus for the hot paths, Python for coordination and rapid iteration.

A node's life cycle follows a clear pattern. Initialize the node with a name. Set up publishers, subscribers, services, and parameters. Enter the main loop, processing callbacks and doing work. Handle shutdown cleanly. This pattern applies in both languages.

Writing a subscriber involves defining a callback function that runs every time a message arrives. Keep callbacks fast and non blocking; do heavy computation elsewhere or at controlled rates. Writing a publisher involves creating the publisher and publishing messages at an appropriate rate.

Timers are for periodic work: a control loop that must run at fifty hertz uses a timer calling a function at fixed intervals, cleaner than sleeping in loops.

Services and actions in code follow patterns too: a service server defines the handler computing responses from requests; a service client sends requests and processes replies. Action servers manage goals, feedback, and results with more structure; the provided frameworks handle much of the boilerplate.

Let me give practical engineering guidance. First, structure your code: separate the ROS communication layer from your algorithm logic, so you can unit test algorithms without ROS and reuse them elsewhere. Second, use parameters for all tunables. Third, handle errors gracefully: sensor timeouts, failed connections, invalid data. Fourth, write unit tests for your algorithms and integration tests for your nodes. Fifth, use version control from the first day; every package should be a repository with history.

Message types: use standard types where they exist. When you define custom messages, keep them minimal and stable; message changes ripple through the system.

Lifecycle and composition: in ROS two, lifecycle nodes formalize states like configuring, activating, and deactivating, helping managed systems. Node composition runs multiple nodes in one process for efficiency while keeping modularity.

Let me describe a worked example: a simple obstacle stopping node. The node subscribes to laser scan topics and publishes velocity commands. In the callback, find the minimum distance in the forward sector; if closer than a threshold, publish zero speed; otherwise publish forward speed. Wrap it as a timer running at ten hertz. Test it first in simulation with a simulated scanner, then record a bag from a real robot and replay to verify. This small project exercises the full node programming workflow.

Real life practicals. A robotics team in Nigeria maintains a mixed Python and C plus plus codebase: C plus plus for the motor controller at high frequency, Python for mission logic. Students in a ROS course write obstacle stopping nodes and race their robots in a corridor, learning timing and tuning viscerally. Good code is boring code: clear names, small functions, tested algorithms, and graceful failures.

A practical habit: keep a snippet library of your own tested ROS patterns: subscriber template, timer loop, service server, parameter loading. Reuse your own proven code rather than retyping it.

PART 7 - ROBOT MODELING, TRANSFORMS, AND SIMULATION

Let me walk you through describing robots and bringing them to life in simulation, two skills that define ROS competence.

Robot modeling starts with the Unified Robot Description Format, an XML file describing the robot's structure: links as rigid bodies, joints connecting them with types and axes, and visual and collision geometry. Sensors are attached to links. The description file is the single source of truth for your robot's structure; every tool, from simulation to visualization to motion planning, reads it.

The visualization tool displays the robot model from the description file. Seeing your robot model correctly is the first test of your description file: are the wheels attached where they should be, is the laser mounted at the right height.

Coordinate frames and transforms are the skeleton of robot software. A robot has many frames: the base, each wheel, the laser, the camera, the map, the odom frame. The transform tree holds the relationships between all these frames at any moment, and the transform library lets any node ask questions like where is the laser relative to the base. Static transforms describe fixed relationships; dynamic transforms update as the robot moves. Keeping the transform tree consistent is a daily duty of ROS engineers.

Simulation brings your robot to life without hardware. The Gazebo simulator loads your robot description, adds physics, sensors like simulated lasers and cameras, and a world with obstacles. You program against the simulated robot exactly as you would the real one. This is revolutionary for development: algorithms are born and matured in simulation, then transferred to hardware.

Sensor plugins in simulation emulate real sensors: laser scanners with configurable noise, cameras with lens models, inertial measurement units with drift. Simulated sensors with realistic noise prepare your algorithms for real data.

Physics fidelity matters. Simple physics runs fast for algorithm work; higher fidelity models help with dynamics and contact. Choose fidelity to your question.

The sim to real transfer, our recurring theme, is managed with discipline. Verify behaviors in simulation first. Introduce noise and delays. Test incrementally on real hardware. Keep parameters adjustable for the differences. Expect a gap and design for it.

Real life practicals. A Nigerian robotics course has students build a simple two wheeled robot description, load it in simulation with a virtual laser, and run navigation algorithms entirely in simulation before the hardware lab session. A startup designing a delivery robot spends four months in simulation refining navigation before their first hardware build, saving enormous cost. An agricultural robotics team models their field robot with camera and arm, testing perception pipelines on simulated fields first. Model carefully, simulate thoroughly, then touch hardware.

A practical habit: version your description files alongside your code and regenerate documentation from them. The robot's structure is living data, and keeping it accurate prevents a family of downstream bugs.

PART 8 - NAVIGATION STACKS AND PERCEPTION PIPELINES

Let me walk you through the two flagship ecosystems in ROS: navigation and perception.

The ROS navigation stack is a complete system for mobile robots moving autonomously in environments. Let me describe its architecture and how you use it. The input is sensor data: laser scans or depth images, plus odometry from wheels or other sources. A localization module estimates where the robot is in a map, commonly with adaptive Monte Carlo localization, which maintains a cloud of possible robot poses and updates them as laser data arrives. A mapping module builds the map, commonly with simultaneous localization and mapping algorithms, often the gmapping or cartographer packages.

The costmap converts the map and live sensor data into a grid of traversal costs: free space, obstacles, and unknown areas, with inflation around obstacles so the robot keeps clearance. The global planner computes a path from the current pose to the goal across the costmap. The local planner follows that path while reacting to immediate surroundings, producing velocity commands. The recovery behaviors handle stuck situations: rotating to clear sensor blind spots, backing up, or clearing costmaps.

Configuring navigation is a practical skill: tuning costmap inflation, planner tolerances, robot footprint, and velocity limits. Real robot navigation is won or lost in tuning, and simulation gives you the hours needed to tune well.

Perception pipelines process sensor data into understanding. A typical vision pipeline: camera images flow through a driver node, then preprocessing nodes for calibration correction and filtering, then detection nodes running algorithms or learned models, then tracking nodes linking detections over time, and finally interpretation nodes feeding planners. Each stage is a node or nodes with topics between them.

Camera calibration is foundational: determining the camera's intrinsic parameters so pixel measurements convert correctly to angles and distances. Laser and depth processing converts raw scans into point clouds, segments obstacles, and extracts features. Fusion combines camera, laser, and odometry for robust perception.

Deep learning integrates smoothly: a trained neural network runs as a node subscribing to images and publishing detections. ROS does not care whether the detection algorithm is classical or learned.

Real life practicals. A Nigerian robotics startup configures the navigation stack for their delivery robot in office buildings, tuning costmaps after observing the robot hug walls too closely. A student team builds a perception pipeline detecting colored objects on a conveyor for a pick and place demo, running neural inference as a ROS node. An agricultural robot team fuses camera and GPS through ROS topics to map weed locations. Reuse the excellent open source building blocks, then focus your effort on the parts unique to your application.

A practical habit: when configuring navigation or perception, change one parameter at a time and record the result. Batch changes create confusions that cost hours; disciplined tuning converges steadily.

PART 9 - PACKAGES, WORKSPACES, BUILD SYSTEMS, AND MULTI ROBOT SYSTEMS

Let me walk you through the engineering infrastructure that keeps ROS projects organized and the extensions for multi robot and real systems.

Packages are the unit of ROS software. A well designed package has a single clear purpose: a driver package for one sensor, an algorithm package for planning, an application package for one robot's mission. Each package declares its dependencies: what other packages it needs. Dependency hygiene prevents fragile builds.

The build system compiles your code and generates message types. In ROS one, catkin organizes packages in a workspace you build with catkin make or catkin build. In ROS two, colcon builds workspaces with modern conventions. The workspace structure keeps source code, build artifacts, and installed files organized. After building, source the workspace so the system finds your packages.

Version control is non negotiable. One repository per package or per cohesive group, with meaningful commits. Teams also use repositories of configuration, called meta repositories, to pin versions of dependencies for deployments.

Launch organization mirrors code organization: top level launch files compose component launches, with arguments selecting simulation or real hardware. Keep launch files declarative and readable.

Multi robot systems extend ROS elegantly through namespaces. Assign each robot a unique namespace: robot one, robot two. All topics, services, and frames are then namespaced, and identical software runs on every robot without collisions. The transform library supports frame prefixes per robot. Centralized coordination nodes can subscribe to all robots topics and publish coordinated commands.

Distributed systems run nodes across multiple computers with configuration of the master location and network settings. Common split: heavy perception on an on board computer, control on a real time computer, monitoring on a base station. Bandwidth management, compressing images and limiting rates, keeps networks healthy.

Real time considerations matter for control. ROS one is not hard real time; control loops requiring determinism run on dedicated real time controllers or microcontrollers, with ROS handling high level coordination. ROS two improves real time support with quality of service settings that control reliability and latency of message delivery.

Deployment practices: use containers for reproducible environments, monitor running systems with logging and remote introspection, and keep configuration under version control separate from code where it aids operations.

Real life practicals. A Nigerian robotics company organizes their delivery robot code into driver, navigation, perception, and application packages, with a meta repository pinning versions per release. A university lab runs a two robot collaborative transport project with namespaces and a coordinator node, learning multi robot debugging. A field team deploys with Docker images on robot computers, updating over the air with care. Structure is not bureaucracy; structure is how complex robot systems stay reliable and maintainable.

A practical habit: write a short README in every package explaining its purpose, nodes, and how to run it. Your future teammates and future you will be grateful.

PART 10 - BEST PRACTICES, CAREERS, AND COURSE COMPLETION

Let me close our course with professional best practices, career guidance, and a synthesis of your learning.

Best practices in ROS development. Design first: sketch your node graph and interfaces before coding. Keep nodes small and focused. Prefer standard interfaces for ecosystem compatibility. Separate algorithm logic from ROS glue for testability. Parameterize all tunables. Test in simulation before hardware, and with recorded bags for regression. Use version control and code review. Log meaningfully. Document packages and launch files. And design for failure: sensors time out, networks drop, hardware breaks; graceful handling distinguishes professional systems.

Common pitfalls to avoid. Forgetting to source setup files. Topic name mismatches between publisher and subscriber. Blocking callbacks that starve the event loop. Hard coded values that break on the next robot. Ignoring timing and latency until integration. Skipping simulation because hardware is exciting. And not reading error messages carefully. Each of these has cost teams hours; learn from their pain.

Careers where ROS skill shines: robotics software engineer, the most direct path; autonomy engineer for vehicles and drones; perception engineer integrating sensors and AI; field robotics engineer deploying and maintaining robots; simulation engineer; and research engineer in universities and labs. Industries from logistics to agriculture to manufacturing to healthcare hire ROS skill. In Africa, robotics startups and automation programs increasingly list ROS explicitly in job descriptions. A portfolio of ROS projects, a simulation navigation demo, a perception pipeline, a documented multi robot project, opens doors.

Study plan for mastery. Weeks one and two: set up the environment, run tutorials, write a simple publisher and subscriber. Weeks three and four: services, actions, parameters, and launch files; build a small robot in simulation. Weeks five and six: description files, transforms, and simulation with sensors. Weeks seven and eight: configure navigation and tune it in simulation. Weeks nine and ten: build a perception pipeline and integrate it. Weeks eleven and twelve: capstone: a complete simulated robot mission, documented, with recorded demonstration and a written report. This portfolio is your professional calling card.

Glossary of Key Terms

ROS: Robot Operating System, a framework for robot software development. Node: a single purpose program in a ROS system. Topic: named channel for continuous publish subscribe messaging. Message: typed data packet sent between nodes. Service: synchronous request response communication. Action: long running goal with feedback and cancellation. Parameter: configurable value read by nodes at runtime. Master: registry connecting publishers and subscribers in ROS one. Package: unit of ROS software with code and metadata. Workspace: directory organizing packages for building. Catkin: build system for ROS one. Colcon: build system for ROS two. Launch file: configuration starting multiple nodes together. Namespace: prefix grouping topics and nodes. Remapping: redirecting a node's topic names. RViz: visualization tool for robot data. Bag file: recorded topic data for replay. Gazebo: physics based robot simulator. URDF: robot description format with links and joints. Transform tree: relationships between coordinate frames. Odometry: estimated robot motion from wheel or sensor data. Localization: estimating robot pose in a map. Mapping: building a representation of the environment. Costmap: grid of traversal costs for navigation. Global planner: path planning across the map. Local planner: velocity control near the robot. Adaptive Monte Carlo localization: particle filter pose estimation. Simultaneous localization and mapping: building maps while localizing. Quality of service: delivery policy settings in ROS two. Lifecycle node: node with managed states like configure and activate. Point cloud: set of three dimensional points from depth sensors. Camera calibration: determining camera imaging parameters. Sim to real gap: differences between simulation and hardware behavior. Real time system: system guaranteeing timing deadlines. Microcontroller: small embedded computer for control tasks. Continuous integration: automated building and testing of code changes.
